# Cloudflareバックエンドの3タスク

2026-10-18作成。実行はユーザーの指示で開始する。このファイル作成だけでは、実装・エージェント起動・push・PR・デプロイを開始しない。

## 目的と担当境界

採用の主デモに必要なCloudflare側のバックエンドを完成させる。
面談情報を保存し、社員への確認依頼、引き受け、回答を同じ案件につなぐ。

音声受付、Decisions、採用Agents、MCP・Eventsは、別担当の[Issue #3](https://github.com/pupuchan1/future-company/issues/3)と[Draft PR #4](https://github.com/pupuchan1/future-company/pull/4)との接続を扱う。同じ仕組みを独立に作り直さない。
黒電話の実機と人間への通話引き継ぎは別担当。FEは既存のReact雛形を使う。

## 現状

ローカルの`r74`に未コミットの途中実装がある。開始前に実ファイルとGit状態を確認し、既存変更を保持する。

- 案件API、DO保存、社員依頼の引き受け・回答、WebSocket同期がある。
- D1には`cases`の要約保存と架空の注文データがある。
- 採用面談の専用送信APIはない。社員回答はまだ`stockAvailable`を必須としている。
- Worker入口では社員認証が未注入。OpenAI用APIと他担当のプロトタイプは未接続。

## 並行開始前に固定する契約

次は採用向けの追加契約案。3担当が同じ内容を使える状態にしてから並行開始する。

- 既存の`caseId`、`commandId`、`expectedRevision`を使う。
- 面談送信は`POST /api/v1/cases/:id/recruitment/submit`。応募職種、経験、質問を受け、本人申告として保存する。
- 採用の社員依頼も既存の`claim`・`answer`を使う。採用では在庫入力を要求しない。
- 更新結果とWebSocketは同じ`CaseSnapshot`を使う。社員向けと来訪者向けの公開範囲を分ける。
- 案件状態の正本はDO。D1は一覧・保存結果を持ち、古いrevisionで新しい要約を上書きしない。
- PR #4との間で、案件ID、面談情報、社員依頼、回答の入出力を合わせる。接続経路が違う場合は着手前に契約へ反映する。

## 並行作業のルール

1. 各担当は上記の所有ファイルだけを編集する。共有ファイルはタスク3が編集する。
2. `contracts.ts`はタスク2だけが編集する。契約変更は他の2担当へ伝えてから反映する。
3. APIと保存処理の接続では、タスク3が関数を提供し、タスク1が呼び出す。相手のファイルを直接編集しない。
4. 実装は同時に進め、最後のWorker入口への組み込みと通し試験はタスク3が順に行う。
5. レビューは追加しない。変更に必要な型チェック・テスト・動作確認を行う。
6. DOに`setInterval`、定期polling、独自ping、無限retryを追加しない。
7. 進捗は実装・接続・実測を区別してGitHub Issueへ共有する。
8. ユーザーの指示なしにpush、PR作成、デプロイ、外部設定変更を行わない。
